# Memorex / Tandy VIS Homebrew Quickstart

This guide explains the shortest known workflow for creating a VIS `CONTROL.TAT` file for homebrew projects.

The goal is not to teach the entire VIS development process. The goal is only to get you from wanting to author a program and getting input into the algorithm the system needs:

```text
vendor number + product number + license class
```

to getting the file the system needs to get your homebrew to boot:

```text
CONTROL.TAT
```

Once you have `CONTROL.TAT`, the rest of the title, application, menu, executable, assets, and disc-building process is up to you.

## What this guide does

This guide shows how to:

1. Generate a VIS registration key with the Python script.
2. Paste that key into a MAKETAT job file.
3. Run `MAKETAT.EXE`.
4. Produce `CONTROL.TAT`.

## What this guide does not do

This guide does not explain how to:

- Write a VIS application.
- Write a Modular Windows application.
- Build a complete VIS disc image.
- Create menus, graphics, sound, or title assets.
- Emulate or burn final VIS discs.

For the broader VIS development files, examples, and documentation, see:

```text
https://github.com/TJBChris/memorex_vis/tree/main
```

## Background

The original VIS title-registration workflow used two main tools:

```text
REGISTER.EXE
MAKETAT.EXE
```

`REGISTER.EXE` was the Tandy-side registration tool. It read a `REGISTER.DAT` file containing vendor and product information, then produced a 20-character registration key.

`MAKETAT.EXE` was the title-control builder. It read a job file containing that registration key and produced `CONTROL.TAT`.

The modern homebrew workflow replaces `REGISTER.EXE` with a Python script.

Original-style workflow:

```text
REGISTER.DAT -> REGISTER.EXE -> registration key
registration key + job file -> MAKETAT.EXE -> CONTROL.TAT
```

Homebrew workflow:

```text
Python key generator -> registration key
registration key + job file -> MAKETAT.EXE -> CONTROL.TAT
```

## Required files

You need three things.

### 1. Python registration key generator

From this repository:

```text
vis_register.py
```

This script recreates the VIS registration key generation behavior.

### 2. MAKETAT.EXE

Get `MAKETAT.EXE` from the `memorex_vis` repository:

```text
https://github.com/TJBChris/memorex_vis/tree/main/tandy/NTSCDISC/DISC
```

That folder also contains related sample files, including `JOBMENU` and BMP files used by the sample menu disc.

### 3. A MAKETAT job file

The best simple starting point is the generic `JOBD` file:

```text
https://github.com/TJBChris/memorex_vis/blob/main/tandy/register/JOBD
```

`JOBD` identifies itself as an example VIS start-up control file for single-application discs.

Use it as your starting template.

## Recommended license class

Known classes:

```text
A = Authorized VIS title, likely associated with VIS logo use
B = Recognized by some code paths, but rejected by the recovered MAKETAT version
C = Non-logo / non-authorized title class
D = Rumored, but not supported by the recovered REGISTER/MAKETAT tools analyzed so far
```

For homebrew and preservation work, use Class C unless you have a specific reason to do otherwise.

Class A appears to imply an officially authorized VIS title and VIS logo use.

## Step 1: Pick your values

Choose:

```text
vendor number
product number
license class
```

For example:

```text
Vendor:  500
Product: 1
Class:   C
```

The vendor and product values are numeric and have a range.  See the Python source code for those ranges.

The class is a letter. For homebrew, use `C`.

## Step 2: Generate a registration key

Run the Python script.

Example:

```bash
python3 vis_register.py --vendor 500 --product 1 --class C
```

The script will output a 20-character registration key.

Example output format:

```text
Vendor:  500
Product: 1
Class:   C
Key:     <generated-key>
```

Copy the generated key exactly.

The key uses a custom alphabet. Punctuation, capitalization, and every character matter.

Do not add spaces.

Do not remove punctuation.

Do not change capitalization.

## Step 3: Copy JOBD to a local job file

Download or copy the `JOBD` template from:

```text
https://github.com/TJBChris/memorex_vis/blob/main/tandy/register/JOBD
```

Save a local copy next to `MAKETAT.EXE`.

For example:

```text
MYTITLE.JOB
```

or:

```text
JOBD
```

The exact filename is less important than giving `MAKETAT.EXE` the correct file when you run it.

## Step 4: Replace the REGISTER line

Open your job file in a plain-text editor.

Find the `REGISTER` line.

It will look conceptually like this:

```text
REGISTER <some-registration-key>
```

Replace the existing key with the key generated by the Python script.

Example:

```text
REGISTER <paste-your-generated-key-here>
```

Do not include angle brackets in the real file.

Use the actual generated key.

## Step 5: Check the TITLE line

The job file should contain a title line.

It will look conceptually like this:

```text
TITLE "My VIS Title"
```

You may change this to your own title.

Example:

```text
TITLE "VIS Homebrew Bootstrap"
```

## Step 6: Understand the PROGRAM line

The job file's `PROGRAM 1` line controls what the VIS starts after `CONTROL.TAT` is accepted.

In the generic `JOBD` example, the sample program line launches a startup executable.

Conceptually:

```text
PROGRAM 1 "A:cardtal2.exe"
```

For your own project, the program named here must exist on the final VIS disc.

You have two choices:

### Option A: Keep the existing PROGRAM line

If you keep the existing program line, then your final disc must include that exact executable at that exact path.

### Option B: Change PROGRAM 1 to your own first-stage loader

For homebrew, a stable first-stage loader is usually cleaner.

For example:

```text
PROGRAM 1 "A:VISBOOT.COM"
```

or:

```text
PROGRAM 1 "A:START.EXE"
```

Whatever you put here must exist on the final disc.

Do not change this line randomly. `CONTROL.TAT` is generated from the job file, so changing the startup target means you need to run `MAKETAT.EXE` again.

## Step 7: Run MAKETAT.EXE

Put these files in the same working directory:

```text
MAKETAT.EXE
your job file
```

Run `MAKETAT.EXE` in DOS, DOSBox, or another DOS-compatible environment.

Example:

```dos
MAKETAT MYTITLE.JOB
```

Or, if your job file is named `JOBD`:

```dos
MAKETAT JOBD
```

If the registration key is valid and the job file is accepted, `MAKETAT.EXE` should produce:

```text
CONTROL.TAT
```

## Step 8: Use CONTROL.TAT

The VIS boot process looks for:

```text
A:\CONTROL.TAT
```

(Where A:\ is the VIS CD drive)

Put the generated `CONTROL.TAT` on the VIS disc.

But in practice, `CONTROL.TAT` must launch something. The job file's `PROGRAM 1` line controls what the VIS starts after `CONTROL.TAT` is accepted.

For this guide, we stop at generating `CONTROL.TAT`.

The rest of VIS development, including writing the executable, building a Modular Windows app, arranging assets, and creating the final disc image, is left to you.  For the broader VIS development files, examples, and documentation, you can check out TJBChris' GitHub repo, or check out his YouTube channel.


## Troubleshooting

### MAKETAT says the registration code is invalid

Check:

```text
Vendor number
Product number
License class
Key spelling
Capitalization
Punctuation
Extra spaces
```

The key must be copied exactly.

### MAKETAT rejects Mode B

That is expected with the recovered version analyzed so far.

Use Class A or Class C.

For homebrew, use Class C.

### Class D does not work

Class D is rumored, but the recovered tools analyzed so far do not support it.

The key format can theoretically encode additional class values, but the recovered `MAKETAT.EXE` accepts A and C, explicitly rejects B, and does not accept D.

### The VIS does not boot the disc

Check that the final disc contains:

```text
CONTROL.TAT
```

Also check that the executable named by the job file's `PROGRAM 1` line exists on the final disc.

If `PROGRAM 1` says:

```text
PROGRAM 1 "A:VISBOOT.COM"
```

then the final disc must contain:

```text
VISBOOT.COM
```

### The title starts but then fails

That usually means `CONTROL.TAT` was accepted, but the program launched by `PROGRAM 1` failed.

At that point, the issue is likely in the application, loader, file paths, assets, disc layout, or runtime environment.

That is outside the scope of this guide.
